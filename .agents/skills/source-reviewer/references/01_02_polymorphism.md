## 2. ポリモーフィズム成立の 4 大判定ポイント (合否基準)

継承によるポリモーフィズムが正しく成立しているかは、下記 4 項目を満たしているかで判別される：

| # | 判定項目 | 合格基準 | 不合格・減点リスク |
| :--- | :--- | :--- | :--- |
| **1** | **基底クラスの仮想関数** | 基底クラスに `virtual` 関数（または純粋仮想関数 `= 0`）が宣言されている | 非仮想関数を派生クラスで同名再定義（Hide）している |
| **2** | **派生クラスのオーバーライド** | 派生クラスがその仮想関数を `override` 指定子付きでオーバーライドしている | `override` がなくシグネチャ不一致のバグを放置 |
| **3** | **多態性呼び出し** | 基底クラスのポインタ（`Base*`）または参照（`Base&`）を介して派生クラスの振る舞いを呼び出せている | 派生クラス型で個別に抱え込み、型判別分岐している |
| **4** | **基底クラスの virtual デストラクタ** | **基底クラスに `virtual ~Base() = default;` がある（メモリリーク防止）** | 仮想デストラクタがなく基底ポインタ delete 時に派生メンバがリーク |

## 3. 減点対象となるアンチパターン (だめな例)

### ❌ アンチパターン①: 共通ではない機能を基底クラスに無理やり追加する
- **症状**:
  ```cpp
  class Bird {
  public:
      // 飛ぶ機能
      virtual void Fly() = 0;
      virtual ~Bird() = default;
  };

  class Penguin : public Bird {
  public:
      void Fly() override {
          // ペンギンは飛べない！ 空実装 or 例外
      }
  };
  ```
- **問題点**: 既存のほとんどの鳥系クラス（`Eagle`, `Sparrow`, `Crow`）が飛べるからといって、飛べない鳥（`Penguin`）がいるにも関わらず基底 `Bird` に `Fly()` を持たせるのは誤り（リスコフの置換原則 LSP 違反）。
- **解決策**: 2段階の継承にして、中間に `FlyingBird` クラスを挟む。
  ```cpp
  class Bird { /* 共通機能 (呼吸, 移動など) */ };
  class FlyingBird : public Bird { virtual void Fly() = 0; };
  class Penguin : public Bird { /* 泳ぐなど */ };
  ```

### ❌ アンチパターン②: is-a 関係の崩壊（ポリモーフィズム目的の不正継承）
- **症状**:
  ```cpp
  class Bird {
  public:
      virtual void Walk() = 0;
      virtual ~Bird() = default;
  };

  class Dog : public Bird { // ！？
  public:
      void Walk() override { /* 犬の歩行 */ }
  };
  ```
- **問題点**: `Walk()` 関数をポリモーフィズムで利用したいからといって `Bird` を継承すると、「`Dog` は `Bird` である（Dog is-a Bird）」という破綻した継承関係になる。
- **解決策**: 基底クラスを `Animal` や `Creature` に名称・責務を変更・抽象化する。

## 4. 例外規定 (免除対象)

以下のいずれかに該当し、正当な理由を明確に説明できる場合はポリモーフィズムの適用除外（または別手法採用）が認められる：

1. **※1. 極限まで抽象化した結果アプリ層に残っていない場合** は例外的にOK。
2. **※2. template やデータドリブン（DoD: Data-Oriented Design）を採用しており、そうすべき理由を明確に説明できる場合** は例外的にOK。
   - 例: 大量インスタンス（`DebrisComponent`）の連続メモリ更新。仮想関数テーブルルックアップ（vtable）のオーバーヘッドを避けるための構造化配列設計。

## 5. 本プロジェクト（GravityShooter）でのポリモーフィズム適用実績

1. **State パターン（単元 01_03 連携）**:
   - `IRailShooterEnemyState` ➔ `Approach`, `Combat`, `Dive`, `Disengage`
   - `ITitleMenuState` ➔ `Idle`, `OpeningModal`, `Suspended`, `Launching`
   - `ITitleLaunchState` ➔ `Charge`, `Accelerate`, `Break`, `Afterglow`
   - `IBossState` ➔ `Phase1`, `Phase2`, `Down`, `Dead`
2. **コンポーネントシステム（ECS風アーキテクチャ）**:
   - `Component` 基底 ➔ 全具象コンポーネント（`Initialize()`, `Update()`, `OnDestroy()` の多態呼び出し）
3. **シーン管理**:
   - `BaseScene` 基底 ➔ `TitleScene`, `GameScene`, `ResultScene`, `SelectScene`
4. **描画パイプライン / オブジェクト**:
   - 各種レンダラーオブジェクトの共通描画インターフェース
