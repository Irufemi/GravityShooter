# 単元: 02_06 マジックナンバー撲滅 (Eliminate Magic Numbers)

学校の授業資料 `02_06. マジックナンバー撲滅` に基づく、ソースコードレビュー基準・アンチパターン集、およびマジックナンバー解消レベル（3段階）のガイドラインです。

---

## 1. 単元の目的と背景

> **「個人就職作品のプロジェクトについて、マジックナンバーを撲滅せよ」**

### マジックナンバーとは？
プログラム中に直接書かれた **「意味の分からない数値定数（ハードコードされたリテラル）」** のこと。

### なぜマジックナンバーを撲滅すべきなのか？
1. **意図が読み取れない（可読性の破綻）**:
   - `if (age > 65)` や `drawButton(100, 200, 150, 50);` など、なぜその数値なのか、何を意味しているのかがコードから伝わらない。
2. **修正漏れ・デグレの温床**:
   - 同じ意味の数値が複数箇所に直接書かれていると、仕様変更時に 1 箇所だけ直し忘れて不整合や重大バグを引き起こす。
3. **ゲーム開発におけるイテレーション効率の低下**:
   - ゲームバランスや見た目の微調整のたびに、プログラマーがソースコードを書き換えて再コンパイル・再起動する必要が生じる。
   - プランナーやアーティストが自分で調整できず、開発チームの分業が阻害される。

---

## 2. マジックナンバー解消の 3 段階アプローチ (企業評価順)

授業資料では、解消アプローチとして 3 つのレベルが提示されています。**難易度が高いほどゲーム会社からの評価も跳ね上がります**。

```
【評価・難易度】
  Level 3 (最高評価) : ImGui等によるリアルタイム編集 ＆ 外部ファイル保存機能
        ▲
  Level 2 (高評価)   : 調整値の外部ファイル化 (JSON / CSV) ＆ ホットリロード
        ▲
  Level 1 (最低限)   : コード内定数化 (constexpr / const / static const)
```

| レベル | 解消手法 | 適用対象・具体例 | 企業・審査員の評価ポイント |
| :--- | :--- | :--- | :--- |
| **Level 1**<br>（最低限の解消） | **名前付き定数化**<br>(`constexpr` / `const` / `enum`) | ・ゲームルール上変わらない固定値（画面アスペクト比 16:9, 円周率 PI, 最大同時発音数など）<br>・クラス固有定数（`static constexpr float kDefaultFov = 60.0f;`） | 「数値に意味を与え、可読性と保守性を意識できている」基礎力の証明。 |
| **Level 2**<br>（高評価） | **調整データの外部ファイル化**<br>(JSON / CSV 等) | ・プレイヤーや敵のHP、移動速度、攻撃力、クールタイム、出現タイミングなど<br>・データテーブルやパラメータシートからの動的読み込み (単元 02_01 / 02_02) | 「プログラマー以外（企画・デザイナー）とのチーム分業・制作効率化を考慮した設計ができる」応用力の証明。 |
| **Level 3**<br>（最高評価） | **インゲーム・エディタ化**<br>(ImGui編集 ＆ ファイル書き戻し) | ・ImGui インスペクターでのスライダー・ドラッグ編集<br>・ゲームを実行したままリアルタイムに数値を確認・調整し、ボタン一つで元の JSON へ保存できる仕組み | 「商用ゲームエンジンのような開発ツール・パイプラインを自作できる」ハイレベルな技術力の証明。 |

## 3. 「許されるマジックナンバー」の例外規定

授業資料スライド 4 に明記された通り、**「誰が見ても数値状態で意味が伝わる一般的なイディオム」** は例外的に許容されます。

| 許されるケース | 例 | 理由 |
| :--- | :--- | :--- |
| **ループの初期値・増分** | `for (int i = 0; i < count; ++i)` | `0` や `1` は配列走査やカウンタの自然な開始値・歩進値であるため。 |
| **パーセンテージの基準** | `if (progress >= 100.0f)` | `100` や `0` は百分率の自明な境界値であるため。 |
| **未選択・無効インデックス** | `int selectedIndex = -1;` | `-1` は C/C++ における無効インデックスの慣用句（センチネル値）であるため。 |
| **幾何・数学の単位元** | `Vector3{0.0f, 1.0f, 0.0f}` (上方向Y軸) | 単位ベクトルや原点 `(0,0,0)`、単位行列の `1`。 |

> [!CAUTION]
> **授業資料の警告**:  
> 「ただしあくまで例外であり、**拡大解釈して適用範囲を広げてはいけない**」。  
> 迷ったら名前付き定数にするか、調整パラメータとして外部化すること。

## 4. 減点・指摘対象となるアンチパターン

### ❌ アンチパターン①: 式の中に唐突に現れる生の数値（裸のリテラル）
- **症状**:
  `damage = attack * 1.5f - defense * 0.8f;`
- **問題点**:
  `1.5f` や `0.8f` が補正係数なのかクリティカル倍率なのか第三者には判別不能。
- **改善案**:
  `static constexpr float kAttackMultiplier = 1.5f;`  
  `static constexpr float kDefenseMitigation = 0.8f;`  
  または調整値として `PlayerStatus.json` 等に外部ファイル化。

---

### ❌ アンチパターン②: UI座標・サイズの直接書き込み
- **症状**:
  `drawButton(640, 360, 200, 50);`
- **問題点**:
  画面解像度変更（1280x720 -> 1920x1080）に追従できず、レイアウト調整にプログラマーの手間がかかる。
- **改善案**:
  アンカー＋オフセット設計にするか、`kButtonWidth = 200.0f;` などの定数化、または UI 設定 JSON から読み込む。

---

### ❌ アンチパターン③: ヘッダーファイルに調整値を直接 constexpr で書くことによるリビルド地獄
- **症状**:
  `Player.h` に `constexpr float kPlayerSpeed = 10.0f;` を書き、速度を変えるたびに全プロジェクトのコンパイルが走る。
- **改善案**:
  - 固定値でなければ、ヘッダーにはメンバ変数のみを置き、ソースファイル内（または JSON 設定ファイル）で初期化する。
