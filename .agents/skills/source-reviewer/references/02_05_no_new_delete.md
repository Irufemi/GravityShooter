# 単元: 02_05 new / delete 禁止 (Smart Pointer & RAII)

学校の授業資料 `02_05. new/delete禁止` に基づく、ソースコードレビュー基準・アンチパターン集、およびモダン C++ メモリ管理ガイドです。

---

## 1. 単元の目的と背景

> **「個人就職作品のプロジェクトについて、GE3 [12_01.unique_ptr]を参考にして、自分のコード内に new / delete が一つもない状態にせよ」**
> 
> ※1. `std::unique_ptr::get()` で生ポインタを取り出すのは OK（new / delete していない）  
> ※2. `std::make_unique()` 等が内部的に new / delete するのは OK（自分のコードではない）  
> ※3. 自作メモリアロケーターの内部実装は例外として new / delete を認める  
> ※4. **`std::unique_ptr` でよいところまで無意味に `std::shared_ptr` にするのもやめましょう。**  
> 
> **AI判定用の補足**:  
> DirectX12 の `ID3D12Resource` について、Map したら必ずしも Unmap しなければならないわけではない。DirectX12 ではリソースを一度 Map したらそのポインタを保持し続け、アプリケーション終了まで Unmap しない手法が公式に認められている（**Persistent Mapping / 永続的マッピング**）。

### なぜ生ポインタの new / delete を禁止するのか？
モダン C++（C++11 以降）において、生の `new` / `delete` を使った手動メモリ管理は **「現代のゲームプログラミングにおいて最大のバグ温床」** とされています。

1. **メモリリークの根絶 (RAII原則)**:
   - 例外送出や早期 return（`if (...) return;`）の経路で `delete` の呼び忘れが容易に発生します。
   - スマートポインタ（`std::unique_ptr`, `std::shared_ptr`）はスコープを抜けた瞬間にデストラクタで自動解放されるため、リークが物理的に発生しません。
2. **二重解放 (Double Free) とダングリングポインタの撲滅**:
   - 生ポインタでは解放済みメモリを再度 `delete` してクラッシュしたり、解放後の無効アドレスへアクセスする脆弱性が多発します。
3. **所有権（Ownership）の明示**:
   - そのポインタを「誰が破棄する責任を持つのか」が型（`unique_ptr` か `shared_ptr` か `T*` か）を見るだけで一目瞭然になります。

## 2. メモリ管理・ポインタ使い分けマトリクス

| ポインタの種類・用途 | 推奨される型 | 役割とベストプラクティス |
| :--- | :--- | :--- |
| **単独所有 (独占)** | `std::unique_ptr<T>`<br>(生成は `std::make_unique<T>()`) | **基本はすべてこれを使う**。コピー不可、ムーブのみ可能。オーバーヘッドは生ポインタと完全に同等（ゼロコスト抽象化）。 |
| **共有所有 (複数箇所から生存管理)** | `std::shared_ptr<T>`<br>(生成は `std::make_shared<T>()`) | 複数のオーナーが共有し、最後の参照が切れた時に解放される場合のみ限定使用。**無意味に濫用しないこと（※4）**。 |
| **弱参照 (循環参照防止)** | `std::weak_ptr<T>` | 親子関係や Observer 等で、`shared_ptr` 同士の循環参照によるリークを防ぐ。 |
| **所有権を持たない観察 (非所有)** | 生ポインタ `T*` または参照 `T&` | `ptr.get()` や参照渡しで取得・使用。ポインタの `delete` は絶対に行わない。 |
| **DirectX COMオブジェクト** | `Microsoft::WRL::ComPtr<T>` | DirectX12 リソース（Device, CommandList, Resource等）の参照カウンタ管理。 |
| **定数バッファ等のマッピング** | Persistent Mapping (永続的マッピング) | `Map()` 後、アプリ終了まで `Unmap()` せず生ポインタを保持する手法（公式推奨）。 |

> [!WARNING]
> **授業注記 ※4 の徹底**:  
> 「とりあえず `shared_ptr` にしておく」のは厳禁。`shared_ptr` はコントロールブロック（アトミックな参照カウンタ）のメモリ確保・加減算が発生するため、単独所有で事足りる場面では必ず `std::unique_ptr` を使用すること。

## 3. 減点・指摘対象となるアンチパターン (就職作品審査基準)

### ❌ アンチパターン①: 生の `new` / `delete` の使用
- **症状**:
  `Player* p = new Player();` や `delete p;`、`int* arr = new int[100]; delete[] arr;`
- **改善案**:
  `auto p = std::make_unique<Player>();` や `std::vector<int> arr(100);` に置き換える。

---

### ❌ アンチパターン②: 無意味な `std::shared_ptr` の乱用
- **症状**:
  マネージャーが子オブジェクトを 1 箇所でのみ保持しているのに、安易に `std::shared_ptr` で管理している。
- **授業資料の警告**:
  `std::unique_ptr` でよいところまで無意味に `std::shared_ptr` にするのもやめましょう。
- **改善案**:
  所有権を持つ側を `std::unique_ptr` にし、外部からアクセスする側には `get()` で生ポインタ（または参照）を渡す。

---

### ❌ アンチパターン③: `new` によるスマートポインタの初期化
- **症状**:
  `std::unique_ptr<Enemy>(new Enemy())`
- **改善案**:
  `std::make_unique<Enemy>()` を使用する（例外安全性と可読性の向上）。

---

## 4. 許可される例外事項

1. **特殊メンバ関数の delete 宣言**:
   - `ClassName(const ClassName&) = delete;`
   - これは C++ のコピー・ムーブ禁止構文であり、メモリ解放の `delete` 演算子ではないため完全に正当。
2. **`std::unique_ptr::get()` による生ポインタの観察**:
   - 破棄責任を持たずに参照・呼び出しを行うための生ポインタ利用は正当。
3. **自作メモリアロケーターの内部実装**:
   - PoolAllocator や StackAllocator 等の内部でバッファを確保するための `new` / `malloc` は例外として認可。
4. **DirectX12 の Persistent Mapping**:
   - リソースを一度 Map したら Unmap せず終了までポインタを保持し続ける手法は DirectX12 の公式仕様に合致。
