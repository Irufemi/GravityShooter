# 単元: 02_03 関数化 (Functionalization & OAOO)

学校の授業資料 `02_03. 関数化` に基づく、ソースコードレビュー基準・アンチパターン集、およびOAOO原則に基づくリファクタリングガイドです。

---

## 1. 単元の目的と背景

> **「個人就職作品のプロジェクトについて、自分のコード内のコピペ実装した処理を、片っ端から関数とその呼び出しに置き換えよ」**
> 
> ※1. ここでいう関数とはグローバル関数、メンバ関数、ラムダ式を含む  
> ※2. データドリブン / テンプレート / 継承・ポリモーフィズム / Observer Pattern 等を適切に使用している箇所を技術的に劣化させてまで単なる関数に置き換える必要はない。

### なぜコピペ実装を排除し関数化するのか？
ソフトウェア工学における有名な設計原則に **OAOO原則 (Once And Only Once: 1度だけ、ただ1度だけ)** があります。
「同じ情報や処理は、プログラム中にただ1回だけ表現するべき」という考え方です。

1. **仕様変更に強いコードの実現**:
   - ゲーム開発ではパラメータ計算式や演出手順、ダメージ計算などの仕様変更が頻繁に発生します。
   - コピペ実装していると、変更のたびに全箇所を書き換える必要があり、修正漏れや不一致が重大なバグ（リリース後にユーザーに発見される不具合）を引き起こします。
   - 関数化されていれば、**関数の中身を1箇所書き換えるだけですべての呼び出し元に自動反映**されます。
2. **バグ発生率の低減と一貫性の担保**:
   - コピペしたコードは微妙な変数名の被りや書き換え忘れが起きやすく、挙動が不統一になりやすい傾向があります。
   - 関数化により、常に全く同一のロジックが実行される一貫性が保証されます。
3. **可読性と意図の明確化**:
   - 長い手続き型コードが関数名（`CalculateDamage`, `ApplyKnockback`, `TriggerFlashEffect` 等）に抽象化され、コードの自己文書化（Self-documenting code）が進みます。

## 2. OAOO原則の実現手段マトリクス（使い分け基準）

授業スライドで提示された通り、重複の性質によって最適なアプローチを使い分けます：

| 重複の性質 | 最適なアプローチ | 適用例 |
| :--- | :--- | :--- |
| **同じ数値を使い回したい** | `constexpr` / `enum` / 外部設定ファイル化 | マジックナンバーの定数化、JSONパラメータ化 (02_02) |
| **同じ処理を使い回したい** | **関数化（メンバ関数 / フリー関数 / ラムダ式）** | **本単元 (02_03)**：ダメージ計算式、ベクトル演算、演出トリガー |
| **数値だけ異なるものに同じ処理を使い回したい** | データドリブン (Data-driven) | データテーブル、LUT、Action Table、JSON (02_01) |
| **複数の型に同じ処理を使い回したい** | テンプレート / 継承・ポリモーフィズム | Generics、抽象基底クラス、Driverパターン (01_02) |

> [!IMPORTANT]
> **授業注記の遵守**:
> すでにデータドリブン、テンプレート、継承・ポリモーフィズム、State/Observerパターン等で高度に抽象化されている箇所を、**無理やり単なる関数に劣化（デグレード）させてはならない**。

## 3. 減点・指摘対象となるアンチパターン

### ❌ アンチパターン①: 同一・類似ロジックのコピペ（Duplicated Logic）
- **症状**:
  ダメージ計算式、UI描画の手続き、ベクトル距離・方向判定、タイマー減衰と終了処理などが、別々の関数やクラスに丸ごとコピーされている。
- **改善案**:
  共通ヘルパー関数やメンバ関数（`CalculateDamage()`, `ProcessTimer()`, `LerpVector()` 等）を新設して一本化する。

### ❌ アンチパターン②: クラス丸ごとコピペ（Duplicated Classes）
- **症状**:
  似た振る舞いをする敵や弾、UIボタンを作る際、既存クラスを丸ごとコピーして数行だけ書き換えている。
- **改善案**:
  基底クラスの抽出（継承・ポリモーフィズム）、共通処理の関数化、またはパラメータによる振る舞い切り替え（データドリブン）へリファクタリングする。

### ❌ アンチパターン③: 長大関数内での繰り返し手続き（Inline Duplication）
- **症状**:
  1つの関数内で、ほぼ同じ3〜5行の手続きが変数名だけ変えて連続して書かれている。
- **改善案**:
  関数ローカルの即時ラムダ式（`auto processItem = [&](auto& item) { ... };`）またはループ処理にまとめる。

## 4. 合格要件チェックリスト (Evaluation Checklist)

- [ ] 複数箇所で重複している計算式・アルゴリズムが関数として抽出されているか。
- [ ] 修正時に1箇所を直せば全体に反映される構造（OAOO原則）になっているか。
- [ ] 不要なクラス丸ごとコピペが存在せず、共通ロジックが再利用されているか。
- [ ] 高度なデザインパターン（State, Observer, Driver等）を壊すことなく、適切な粒度で関数化されているか。
