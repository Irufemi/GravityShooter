# ツール名: AI画工のマジックブラシ 開発ロードマップ

## 概要
PythonとGemini APIを用いて、入力画像とプロンプトからHLSLシェーダーコードを自動生成する。さらに、文法的なエラーを直すだけでなく、視覚的な出力結果までAIが確認して自己修復を行う、高度なシェーダー生成・統合システムの開発ロードマップ。
本機能はゲーム本編の進行に干渉しないよう、独立した検証用シーン（`TL1Scene`）内で実装とテストを行う。

## 動作に必要な環境・ソフトウェア
本ツール（ローカルサーバー）を稼働させるPCには、以下のインストールが必要です。
- **Python 3.10以上** （インストール時に `Add python.exe to PATH` を有効にして環境変数を通す）
- **依存パッケージ群**
  - コマンドプロンプト等で `Tools/ShaderGenerator` ディレクトリに移動し、以下のコマンドを実行してインストールしてください。
  - `python -m pip install -r requirements.txt`
  - *(※インストールされる主要パッケージ: `google-genai`, `fastapi`, `uvicorn`, `python-dotenv`, `pillow`, `python-multipart`)*
- **APIキーの設定**
  - `Tools/ShaderGenerator/.env` ファイルを作成し、Gemini APIキーを `GEMINI_API_KEY=あなたのキー` という形式で記述してください。
*(※将来的に他メンバーのPCへ配布する際は、PyInstaller等を用いてPython不要の単体 `.exe` ファイルにビルドすることも検討)*

## Phase 1: ローカルAPIサーバー環境の構築 (Python側) [完了]
- **目標**: Pythonツールを都度起動ではなく、FastAPI等を用いた常駐型のローカルサーバーとして構築する。
- **タスク**:
  - `project/Tools/ShaderGenerator` に FastAPI を用いたサーバー基盤を実装
  - エディタからの「画像 + プロンプト」をHTTP/WebSocketで受け取るエンドポイントの作成
  - 状態（チャット履歴や修復のコンテキスト）を保持しながらGeminiと通信する仕組みの構築

## Phase 2: TL1Scene の構築 (C++ / Application側) [完了]
- **目標**: ゲーム本編から完全に独立した、ツール開発・検証用の専用シーンを用意する。
- **タスク**:
  - `Application_solo/scene/TL1` ディレクトリと `TL1Scene` クラスを新規作成
  - 「AIマジックブラシ専用UIパネル (ImGui)」をこのシーン専用の機能として実装する
  - このシーン内でのみ、後続の生成シェーダーを描画し、テストできる基盤を作る

## Phase 3: エンジン仕様の強制と自動生成 (インターフェース連携) [完了]
- **目標**: IrufemiEngineで確実に動作するシェーダーを生成するための制約を設ける。
- **タスク**:
  - エンジン側で使用する定数バッファ (`cbuffer` の時間や解像度など) やテクスチャレジスタの仕様を定義
  - 上記の仕様をGeminiの「システムプロンプト」に強制ルールとして埋め込む処理の実装
  - 要求に基づき、仕様に準拠したHLSLコードを出力させる

## Phase 4: C++主導のコンパイル検証と自己修復連携 [完了]
- **目標**: 生成されたコードのコンパイルエラーをAI自身に直させる仕組みを、C++エンジン主導で構築する。
- **タスク**:
  - `TL1Scene` 側からPythonサーバー (`/generate` エンドポイント) へ非同期で生成リクエストを投げる処理の実装
  - Python側が返したHLSLをエンジン (`ShaderCompiler`) でコンパイル
  - **自己修復**: エラーが発生した場合、`assert` で落ちずにエラーログを抽出し、Pythonの `/fix_error` エンドポイントに送り返して再生成させるループの実装

## Phase 5: ホットリロードの統合とプレビュー環境 [完了]
- **目標**: コンパイルが通ったシェーダーを即座に画面に反映させる。
- **タスク**:
  - 修復ループを突破（コンパイル成功）したHLSLをテンポラリファイルとして保存
  - 生成されたシェーダーオブジェクトを現在のパイプラインにバインドして再描画（ホットリロード）
  - エディタ上のUI（ImGui）に現在のステータス（「生成中」「エラー修復中」「完了」など）を表示する機能の追加

## Phase 5.5: UX/UIの洗練と使い勝手の向上 (現在進行中)
- **目標**: ツールとしてのユーザビリティを飛躍的に向上させ、より直感的かつ安全に操作できる環境を整える。
- **タスク**:
  - **入出力の分離**: 「AIに見せる参考画像」と「シェーダーにバインドする入力テクスチャ」を明確にUI上で分離し、テクスチャ未指定時には白テクスチャを割り当てる安全なフォールバック処理を実装。
  - **テクスチャ選択のCombo化**: エンジン(`TextureManager`)にロード済みのテクスチャ一覧から、入力テクスチャをプルダウンで直感的に選択できるようにする。
  - **エクスプローラー連携**: 参考画像をWindows標準のファイル選択ダイアログから「参照(Browse)」できるようにする。
  - **ドラッグ＆ドロップ(D&D)対応**: 外部からエディタ画面へ直接画像をドラッグ＆ドロップした際、自動で参考画像としてパスを受け取る機能を実装。

## Phase 5.6: 命名システムとPSOキャッシュの完全ホットリロード対応 (Planning)
- **目標**: プロの開発現場に則したアセット命名ルールの導入と、エンジンの根幹機能(`PSOManager`)を改修し、真のホットリロードを実現する。
- **タスク**:
  - **命名UIの追加**: ImGuiに `Shader Name` (任意) 入力欄を設け、空欄時は `GenShader_MMDD_HHMMSS` のような一意な名前を自動でフォールバック生成する機能を追加。
  - **保存ファイルの動的化**: `temp_generated_shader.hlsl` のような固定名ではなく、指定されたシェーダー名でHLSLファイルを一時保存・コンパイルするように変更。
  - **エンジンの根本改修**: `PSOManager` に、シェーダー名とその生成キャッシュキーをトラッキングする `std::unordered_map<std::string, std::vector<Key>> cacheKeysByName_` を新設。
  - **キャッシュの安全な部分破棄**: 同じ名前のシェーダーが上書き(`RegisterShader`)された際、そのシェーダーに依存する古いPSOキャッシュ群のみを安全に破棄し、新しいキャッシュを再生成させる真のホットリロードを確立する。

## Phase 6: 視覚的フィードバックループの実装 (見た目の自己修復)
- **目標**: 「コンパイルは通ったが、指定した参考画像と見た目が違う」状態をAIに認識させ、自律的に再調整させる。
- **タスク**:
  - ホットリロード後、`TL1Scene` 内で描画されたプレビュー結果をスクリーンショットとしてキャプチャする機能の追加
  - 取得したスクリーンショットをPythonサーバーへ送信
  - Gemini(マルチモーダル)に「参考画像」と「実際の描画結果」を比較させ、シェーダーを再生成させる究極の修復ループ構築

## 補足事項・最新のアップデート
- **別PCでの動作対応 (ポータビリティ向上)**:
  - C++側のPython起動パスを、`GetModuleFileNameA` と `std::filesystem` を使用した実行ファイル基準の動的相対パスに修正しました。これにより、どのPCやどのドライブにクローンしても環境構築（Python等）さえすれば動作します。
- **レート制限（Quota）対策**:
  - Gemini APIの無料枠の制限を回避し、高速な修復ループを回すために、使用モデルを `gemini-2.5-pro` から `gemini-2.5-flash` に変更しました。
- **プロセス管理の堅牢化**:
  - Pythonサーバーの停止時に、子プロセスである `python.exe` がゾンビプロセスとして残りポート8000を占拠し続ける問題に対し、`taskkill` を用いたプロセスツリー全体の強制終了を実装しました。これにより、ImGuiからの「Restart Server」が完全に機能します。
- ※Python側の機能や使い方に関する詳細は `Tools/ShaderGenerator/README.md` を参照してください。
- 作業は `TL1Scene` 内で完結するため、他のゲームロジックや本編のシーンに干渉せず安全に開発を進められます。

## 今後の展望と課題 (先生からのフィードバック対応)
進捗確認にて頂いた非常に重要なフィードバックと、それに対する今後の拡張方針です。

1. **参考画像＋文章プロンプトの送信**
   - **状況**: ✅ 実装済み。現状のPythonサーバー (`/generate` エンドポイント) はGeminiのマルチモーダル機能を使用しており、ImGuiから渡された画像(`image_path`)と文章の両方をAIに送信し、それを基に生成を行っています。
2. **Shader適用後のスクショによるAIの自己評価**
   - **状況**: 🎯 Phase 6の目標と完全に一致。現在の「コンパイルエラーを直す」ループに加え、「適用された画面をキャプチャし、AIに『参考画像と見た目がどう違うか』を自己採点させて再調整させる」究極のループ実装を目指します。
3. **リニアワークフローの意識**
   - **状況**: ⚠️ 今後の重要課題。現在の生成コードは色空間を意識していないため、モニター上で意図した色にならない場合があります。今後はC++エンジンのレンダーターゲットをsRGBフォーマットにするか、AIのプロンプトで「最後に `pow(color, 1.0/2.2)` のガンマ補正をかけること」を指示するなどの対応が必要です。
4. **エンジン非依存の独立ツール化 (.NET等)**
   - **状況**: 💡 移行準備完了。現状でも「PythonのWebAPIサーバー」としてバックエンドは完全にエンジンから独立しています。そのため、現在C++のImGuiで作っているフロントエンド（UIパネル）を C# (.NET / WPF) などで作り直してAPIを叩くようにすれば、すぐに「誰でも使える独立したツールアプリ」になります！
5. **一部オブジェクトへの適用 (マテリアル化)**
   - **状況**: 📝 今後の拡張機能。現状の全画面描画（ポストプロセス/Shadertoy）だけでなく、ImGui上で「PostProcess / Opaque / Transparent」等を選べるようにし、3Dモデルの法線やUVを受け取るオブジェクト用シェーダーとしても出力・適用できるようにする機能拡張を検討します。
