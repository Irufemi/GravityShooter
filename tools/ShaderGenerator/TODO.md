# AI Magic Brush (ShaderGenerator) TODOリスト

このドキュメントは、AIを用いた動的シェーダー自動生成ツール（AI Magic Brush）の今後の拡張計画・残課題をまとめたものです。

## 優先タスク (Next Steps)

### 0. サーバーログの ImGui 統合と黒窓の非表示化（最優先）
Pythonサーバー起動時に発生するコマンドプロンプトの黒窓を完全に非表示にし、バックグラウンドのログ出力をゲーム内のImGuiパネルにリダイレクトしてリアルタイム表示する機能。
- [ ] **[C++側] パイプ通信の構築**
  - `CreatePipe` を用いて子プロセス（Python）の標準出力・標準エラー出力をキャプチャし、`CREATE_NO_WINDOW` と併用して黒窓を防ぐ。
- [ ] **[C++側] ログ読み取りスレッドとタイムスタンプの実装**
  - 非同期でパイプから文字列を読み取り、`[HH:MM:SS]` のようなタイムスタンプを付与してから `std::vector<std::string>` 等のバッファにスレッドセーフに蓄積する。
- [ ] **[C++側] ImGui へのコンソール実装**
  - `TL1Scene` のデバッグUI内にコンソールウィンドウを作成し、取得したサーバーログを一覧表示（自動スクロール付き）する。

### 0.5. 生成履歴機能 (History & Undo)
AIが生成した過去のシェーダーコードを保持し、いつでも前の状態に戻せる機能。
- [ ] **[C++側] 履歴管理バッファの追加**
  - 生成成功したプロンプトとシェーダーコードのペアを保存する履歴リスト（`std::vector`）を作成する。
- [ ] **[C++側] 履歴復元用UIの実装**
  - ImGui内に「履歴 (History)」タブまたはリストボックスを作成し、クリック一つで過去の生成結果に巻き戻し（Undo）して適用・再コンパイルできるようにする。

### 1. 究極の自己修復（Phase 6: 視覚的フィードバックループ）
コンパイルエラーの修正だけでなく、AIに実際のレンダリング結果を見せて「参考画像との見た目の違い」を自己評価・自己修復させる機能。
- [ ] **[C++側] スクリーンショット機能の実装**
  - 画面のレンダーターゲット（バックバッファ）から画像を取得し、ファイルまたはメモリに保存する機構（`DirectXTex` を活用）。
- [ ] **[C++側] VisualEvaluating 状態の追加**
  - コンパイル成功後、自動的にスクショを撮影し、Pythonサーバーに評価をリクエストする一連のフローを構築。
- [ ] **[Python側] `/evaluate_visual` エンドポイントの追加**
  - Gemini APIに「参考画像」と「現在のスクショ」の2枚を渡し、見た目の差異を分析させ、それを修正する新しいHLSLコードを生成させる。

### 2. リニアワークフロー（ガンマ補正）への対応
AIが生成した色と実際のモニタ出力時の色空間のズレを解消する。
- [ ] **[Python側] プロンプト (`system_prompt.txt`) の修正**
  - 色計算をリニア空間で行い、ピクセルシェーダーの最終出力で必ずガンマ補正 (`pow(color, 1.0/2.2)`) を行うよう明示的な制約を追加する。
- [ ] **[C++側] ポストプロセス連携（必要に応じて）**
  - AIシェーダーの出力先を sRGB 対応フォーマットに合わせる、あるいはエンジン側で後処理をかける。

### 3. 一部オブジェクトへの適用対応（マテリアル化）
現状の「画面全体へのポストプロセス（Screen）」だけでなく、シーン内の特定の3Dモデル（Object3D）の表面にAIシェーダーを適用できるようにする拡張。
- [ ] **[C++側] ターゲット選択UIの実装**
  - `TL1Scene` の ImGui で、適用対象を「Screen」か「Object3D」か選択できるようにする。
- [ ] **[C++側] マテリアルへのシェーダーバインド**
  - 生成されたシェーダーを、特定の `GameObject` の `ModelRenderer` などのカスタムマテリアルとしてアタッチ・更新する仕組み。
- [ ] **[Python側] 対象に応じたHLSLテンプレートとプロンプトの切り替え**
  - ターゲットが `Object3D` の場合、頂点形状やUV展開図に依存せずにモデルに模様を綺麗にハメるため、以下の手法をAIに指示する。
  - **手法A (プロシージャル/UV非依存)**: モデルのUVを使わず、ワールド座標(`worldPos`)や法線(`normal`)をベースに模様を計算させる。（例: 上面だけ雪が積もる、Y座標ベースのグラデーション、リムライト等）
  - **手法B (ベーステクスチャ合成)**: C++側から本来のテクスチャ（Base Color等）を `gTexture` として渡し、AIには「その色をベースに発光やノイズエフェクトを加算・乗算して加工しろ」と指示し、元のディテールを維持する。
  - **手法C (Triplanar Mapping)**: 複雑な形状に一貫したノイズ模様を貼るため、UVの代わりにXYZの3方向から模様を投影してブレンドする計算式をテンプレートに組み込む。

## 長期構想 (Future Works)

### 4. .NET/Standalone Tooling (長期的目標)
- **概要**: C++ / ImGui のフロントエンドを C# (.NET) 等の別アプリケーションに分離し、エンジンから独立して動作するツールにする。
- **課題**: 通信プロトコルの策定（TCP/UDP, パイプ等）と、エンジンの外部からシェーダーをホットリロードする堅牢な仕組みが必要。

### 5. 生成プロセス(Gemini)のストリーミング表示機能
- **概要**: APIへのリクエスト中、コンソールが沈黙して止まっているように見える不安を解消するため、Geminiが生成中のテキストをリアルタイムでコンソール（ImGui）にパラパラと出力する。
- **アプローチ**: Python側で `stream=True` を利用して取得し、部分的なテキストを標準出力 (`sys.stdout.write` + `flush`) に随時流し込む。C++側はパイプから読み取った端からImGuiのコンソールに出力する。
